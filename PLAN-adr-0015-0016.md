# Plan: the `/27` rack block floor (ADR 0015) and switch address materialization (ADR 0016)

Implementation plan for two of the three ADRs that came out of the production data
validation (`PROD-DATA-ANALYSIS.md`). **[ADR 0017](docs/adr/0017-derived-same-vlan-addresses.md)
is deliberately not in this plan** — its own Follow-up section says it "is materially larger
than ADRs 0015 and 0016 and should not share a plan with them", and that holds: it changes
the type-port schema, the materialization path, the locked-field rules, rack-slot
validation, and the same-VLAN pre-flight, and it amends ADR 0003.

Both ADRs here are unblocked by anything else, and both are prerequisites for
`PLAN-prod-import.md`.

## Sequencing: two PRs, ADR 0015 first

ADR 0016's tests create racks and assert addresses computed from their blocks. Landing the
floor first means those fixtures get written once, against final arithmetic, instead of
being written against `/29`s and `/30`s and then rewritten. There is no dependency in the
other direction.

The two PRs are otherwise independent and touch disjoint code (`suggestions.py` versus the
`NetworkSwitch` materialization path); only `inventory/tests.py` is common ground.

## Before starting: establish the baseline

`.env` is gitignored and must hold the **local-dev** shape (`.env.example`:
`DJANGO_DEBUG=true`, `DB_PASSWORD=na9000dev`, `DB_HOST=127.0.0.1`), not the deployment shape
(`.env.compose.example`, where `DJANGO_DEBUG=false` is deliberate — see ADR 0009). With the
deployment shape, every test errors on `Access denied for user 'na9000'`, and 9 admin tests
additionally error on `Missing staticfiles manifest entry` because `DJANGO_DEBUG=false`
selects `ManifestStaticFilesStorage` and `collectstatic` has never been run.

Nothing auto-loads `.env` — neither `manage.py` nor `settings.py` uses `python-dotenv` — so
it has to be sourced:

```
set -a && . ./.env; set +a
python manage.py test inventory
```

Baseline is **341 tests, green**. Establish it before changing anything, so a red run later
is unambiguously the code.

# PR 1 — ADR 0015: rack address blocks are never smaller than a `/27`

## The change

`inventory/suggestions.py`, `required_block_size()`:

```python
return max(slot_count + 2, 32)
```

That is the entire production-code change. The floor lives here rather than in
`prefix_length_for_capacity()` because all three call sites need it and inherit it for free:
`prefix_length_for_capacity()` → `suggest_rack_vlan_range()` (the suggester),
`RackVlanRange._validate_range()` (`inventory/models.py:1151`, rejects a hand-entered block
too small for its rack), and `Rack.clean()` (`:937`, refuses to grow `slot_count` past what
existing ranges hold).

The docstring must be updated too — it currently derives `slot_count + 2` from first
principles and says nothing about a floor, which would leave the rationale for the `max()`
undocumented at the one place a reader will look.

## Test fallout — measured, not predicted

**ADR 0015's Follow-up section lists five affected tests. Only three of them actually fail.**
This was verified by applying the one-line change and running the suite, not by reading. Work
from the list below, not from the ADR's.

### Genuinely failing (3)

| Test | Why | Fix |
|---|---|---|
| `SuggestionFunctionTests.test_prefix_length_for_capacity_single_slot` (`tests.py:552`) | `prefix_length_for_capacity(1)` is now `27`, not `30` | Update the expectation and the comment, which currently explains the `slot_count + 2` arithmetic that no longer determines the answer |
| `SuggestionFunctionTests.test_prefix_length_for_capacity_reserves_top_address` (`:560`) | `prefix_length_for_capacity(3)` is now `27`, not `29` | **Needs a rewrite, not a new number.** This test exists to prove the *top address is reserved* — that a naive `slot_count + 1` rule would be wrong. At slot count 3 the floor now decides the answer, so the test would prove nothing. Re-express it above the floor: `prefix_length_for_capacity(31)` must be `26`, since 31 slots need 33 addresses and a `/27`'s 32 are one short — which is only true because the top address is reserved |
| `InlineFormsetSaveTests.test_blank_range_suggested_for_inline_on_unsaved_new_rack` (`:470`) | Suggests `10.200.0.0/27`, not `/29` | Update the expected value |

### Passing, but no longer proving what they were written to prove (2)

Both are named in the ADR as failures. They don't fail — but they now succeed via a different
code path, which is worse than failing, because nothing draws attention to it.

- **`RackVlanRangeValidationTests.test_explicit_range_too_small_for_rack_slot_count_raises`
  (`:886`)** — asserts a `/30` is rejected for a 4-slot rack. It still is, but now because of
  the floor, not because slot 4 falls outside the block. The slot-count arm of
  `_validate_range()` is left with no coverage at all. Split into two tests: keep the `/30`
  case as a floor test, and add a slot-count case above the floor — a `/27` (32 addresses)
  against a 40-slot rack (needs 42) exercises the original branch. Assert on the message, not
  just the exception type, so the two can't silently converge again.
- **`RackValidationTests.test_increasing_slot_count_beyond_existing_range_capacity_raises`
  (`:964`)** — builds a `/29` for a 4-slot rack via `RackVlanRange.objects.create()`, which
  skips validation, so the fixture is constructed in a state `full_clean()` would now reject.
  The assertion still passes because growing to `slot_count=10` is refused either way.
  Restructure around a `/27`: a 4-slot rack with a `/27`, grown to 40 slots, is refused for
  the capacity reason the test is named for. Its sibling
  `test_increasing_slot_count_within_existing_range_capacity_is_fine` (`:975`) already uses a
  `/27` and needs no change.

### Pre-existing bug, in scope to fix

**`RackVlanRangeValidationTests.test_explicit_overlap_with_sibling_range_raises` (`:859`)**
has never tested overlap. It builds a `/28` for a **30-slot** rack, and
`required_block_size(30)` is already `32` today — so the range is rejected for being too
small, and `_validate_range()` returns before reaching the overlap loop. The bare
`assertRaises(ValidationError)` hides this.

The floor doesn't cause this, but it does make it permanent. Note that the obvious repair —
nudging the `/28` to a `/27` at the same base — doesn't work: `10.200.0.16/27` has host bits
set and `IPv4Network(..., strict=True)` rejects it before any overlap check runs. Use a
range that clears the size check and then genuinely overlaps the sibling `10.200.0.0/27`:
either the identical `10.200.0.0/27`, or `10.200.0.0/26` (64 addresses, so comfortably past
the floor, and it contains the sibling). Assert on the overlap message, not just the
exception type, so this can't silently revert to passing for the size reason.

## New coverage

ADR 0015 requires three additions.

1. **The floor at every slot count below 30.** A loop over `range(1, 31)` asserting
   `required_block_size(n) == 32` for `n <= 30`, and `prefix_length_for_capacity(n) == 27`.
   Cheap, pure, and it pins the boundary at both ends: `31` must give a `/26`.
2. **The floor enforced against a hand-entered sub-`/27` range.** Covered by the split of
   `:886` above.
3. **The production replay** — see below.

## The production replay test

This is the evidentiary basis for the whole ADR: replaying the production racks through the
suggester reproduces **19 of 21** bases with the floor, versus **1 of 21** without it. It
should fail loudly if the arithmetic ever drifts.

**The data must be transcribed as literals into `tests.py`.** `prod/` is in `.gitignore`, so
the CSVs are not in the repo and will not exist in CI. The table below is already derived —
slot counts are the maximum occupied slot per rack from
`prod/MPS Audio Network Standards - IP Addressing mk2.csv`, bases are from
`PROD-DATA-ANALYSIS.md` §1.

Build it end-to-end through the model layer (create a `Rack`, then
`RackVlanRange(rack=..., vlan=...)` + `full_clean()` + `save()`), not by calling
`suggest_rack_vlan_range()` directly. The pure-function version would pass even if
`_validate_range()` disagreed with the suggester, which is precisely the class of drift this
test is guarding against.

Setup: VLAN 200, subnet `10.200.0.0/21`, `dhcp_range_start=10.200.0.1`,
`dhcp_range_end=10.200.0.254` (the bottom `/24`, per ADR 0011 — this is what pushes the
first block to `10.200.1.0`). Then create the 19 racks **in this order** — `suggest_rack_vlan_range()`
is first-fit, so creation order determines every base:

| # | Rack | `slot_count` | Expected Control base |
|---|---|---|---|
| 1 | CONTROL | 1 | `10.200.1.0/27` |
| 2 | WPC1SRU | 5 | `10.200.1.32/27` |
| 3 | WPC2SRL | 5 | `10.200.1.64/27` |
| 4 | WPC3SLU | 5 | `10.200.1.96/27` |
| 5 | WPC4SLL | 5 | `10.200.1.128/27` |
| 6 | WPM1SR | 4 | `10.200.1.160/27` |
| 7 | WPM2SL | 4 | `10.200.1.192/27` |
| 8 | WPM3 | 4 | `10.200.1.224/27` |
| 9 | XE300-1 | 4 | `10.200.2.0/27` |
| 10 | XE300-2 | 4 | `10.200.2.32/27` |
| 11 | W8LM1SR | 3 | `10.200.2.64/27` |
| 12 | W8LM2SL | 3 | `10.200.2.96/27` |
| 13 | W8LM3 | 3 | `10.200.2.128/27` |
| 14 | FOH Drive #1 | 2 | `10.200.2.160/27` |
| 15 | FOH Drive #2 | 2 | `10.200.2.192/27` |
| 16 | CDD | 1 | `10.200.2.224/27` |
| 17 | AVIO | 19 | `10.200.3.0/27` |
| 18 | SPARE | 3 | `10.200.3.32/27` |
| 19 | FLOATSWITCH | 3 | `10.200.3.64/27` |

Three notes on this table:

- **`CONTROL`, `CDD` and `SHURE` hold no equipment**, so their honest slot count isn't
  derivable from the addressing CSV. `1` is used above because `Rack.slot_count` has
  `MinValueValidator(1)`. This is safe rather than a guess that matters: under the floor,
  *every* slot count from 1 to 30 yields a `/27`, and production occupancy runs 2–19, so no
  value in the plausible range can change a single expected base. The test is insensitive to
  the transcription being exactly right, which is what makes literals acceptable here.
- **`SHURE` (offset 1280) and `CONSOLES` (offset 1536) are deliberately excluded.** They sit
  behind reserved gaps, and a first-fit suggester never leaves a gap — they must be entered
  by hand. That is ADR 0001 working as intended. The test should assert this explicitly
  rather than omitting them silently: after the 19, a 20th rack must be suggested
  `10.200.3.96/27`, *not* `10.200.5.0/27`, which is exactly why manual entry is required.
- **Add the counter-assertion.** Without the floor this replay produces 1 of 21. A single
  extra assertion — that `prefix_length_for_capacity(2)` is `27` and not `30` — records in
  the test file itself why the replay works, so a future reader doesn't have to reconstruct
  it from the ADR.

## ADR correction

Amend the Follow-up section of `docs/adr/0015-minimum-rack-block-size.md` to match the
measured fallout. The two the ADR cites as `:890` and `:968` —
`test_explicit_range_too_small_for_rack_slot_count_raises` and
`test_increasing_slot_count_beyond_existing_range_capacity_raises` — do not fail, for the
reasons given above. Keep them listed, since they still need work, but describe them as
"passes for the wrong reason" rather than as failures. Add the `:859` overlap-test bug.

Refer to these two by test name, not line number: the ADR's `:890`/`:968` and this plan's
`:886`/`:964` are the same two tests cited from different points in their bodies, and mixing
the conventions is how the ambiguity arises in the first place.

Do not rewrite the decision itself. The decision is correct and unchanged; only its

# PR 2 — ADR 0016: switches materialize their VLAN addresses at creation

## Shape

This mirrors ADR 0013's device path closely enough that
`NetworkDevice.port_addressing` / `_materializes_static()` / `_materialize_ports()`
(`inventory/models.py:2675`–`2790`) should be read first and followed structurally.

1. **`SwitchAddressing(models.TextChoices)`** — `STATIC` and `MANUAL`, alongside
   `PortAddressing` (`:69`). Not a reuse of `PortAddressing`: `NetworkSwitchAddress` has no
   `is_dhcp` field, so a `DHCP` value would have nothing to represent. `MANUAL` means "I will
   add addresses myself", not "this switch has no addresses".
2. **`NetworkSwitch._address_materialization: str = SwitchAddressing.STATIC`** as a private
   class-level default, exposed through an `address_materialization` `@property` with a
   setter that raises `ValidationError` on an out-of-domain value. The property is not
   optional decoration — Django's `Model.__init__` accepts an unknown keyword only when the
   name is a field or a `property` (`opts._property_names`), so a plain class attribute makes
   `NetworkSwitch.objects.create(..., address_materialization=...)` raise `TypeError`.
3. **`_materializes_addresses()`** — `self.rack is not None and self.address_materialization
   == SwitchAddressing.STATIC`. Unracked switches materialize nothing under either choice;
   they are spare pool by definition (`CONTEXT.md`), and `NetworkSwitchAddress.clean()`
   (`:2206`) already rejects a static address on an unracked switch.
4. **`_materialize_addresses()`**, called from `NetworkSwitch.save()` immediately after the
   existing `self._materialize_ports()` in the `if is_new:` branch, inside the
   `transaction.atomic()` already open there. For each `RackVlanRange` on the rack, ordered
   `.order_by("vlan__vlan_id")`:

   ```python
   address = NetworkSwitchAddress(switch=self, vlan=rack_range.vlan, created_by=self.created_by)
   address.full_clean()
   address.save()
   ```

   Construct-blank → `full_clean()` → `save()` is load-bearing and matches ADR 0013 and ADR
   0014 decision 7: `save()`/`objects.create()` never call `clean()`, so a directly-saved row
   would persist a blank address instead of triggering the suggestion. This reuses
   `NetworkSwitchAddress.clean()`'s existing blank-fill (`:2211`) and its
   `_validate_static_address()` call verbatim — **this PR adds no address arithmetic of its
   own.**

   The explicit `order_by` is required despite `RackVlanRange.Meta.ordering = ["vlan", ...]`,
   because ordering by a relation name defers to the related model's own `Meta.ordering`
   rather than to `vlan_id`. ADR 0016 decision 5 wants `vlan__vlan_id` specifically, so a
   failure names the same VLAN on every replay.
5. **Zero ranges on the rack is not an error.** A rack with no ranges produces a switch with
   no addresses, exactly as today. This is where switches are simpler than devices: a device
   *type port* demands a specific VLAN, so a missing range is a contradiction; here the rack's
   ranges *are* the list, so an empty list is trivially satisfied.

## Departure from ADR 0016: there must be a `clean()`-time pre-flight

**ADR 0016 declines a pre-flight and its reasoning is incomplete.** It argues that "the only
remaining failure is a collision, and `_validate_static_address()` already reports those
clearly, so there is nothing a pre-flight would improve." That is an argument about *message
quality*. The actual reason the device side has one is different, and it is recorded verbatim
in `test_admin_add_post_address_collision_renders_form_error_not_500` (`tests.py:2019`, after
ADR 0015's additions shifted it), which was itself a review-council finding:

> Left unconverted, Django's `add_error()` raises a raw `ValueError` for a nonexistent form
> field instead of rendering a validation message — an ordinary Editor submission hitting an
> address collision would 500, not see a form error.

Django's admin calls `save_model()` — and therefore `NetworkSwitch.save()`, and therefore
materialization — **after** form validation has already passed. A `ValidationError` raised
from inside `save()` has no form to attach to. Without a pre-flight in `clean()`, an Editor
who hits an address collision creating a switch gets a 500, reintroducing on the switch side
the exact bug that test was written to prevent on the device side.

So add `_check_address_materialization_possible()`:

- Pure, taking no `pk`, so it can run from both `clean()` (admin form errors) and the top of
  `_materialize_addresses()` (the `objects.create()` path, which never calls `clean()`) —
  same dual-call-site shape as `_check_static_materialization_possible()`.
- For each of the rack's ranges: compute the suggestion via `_suggest_rack_slot_address()`
  and run `_validate_static_address()`.
- **Re-raise as a plain, non-field `ValidationError`.** `_validate_static_address()` raises
  keyed on `"address"`, which is right for `NetworkSwitchAddress.clean()` but wrong for
  `NetworkSwitch.clean()`, whose form has no `address` field. Copy the re-raise at `:2752`
  (`raise ValidationError(exc.messages) from exc`) and its comment.
- Called from `NetworkSwitch.clean()` only when `self._materializes_addresses()` and only on
  the creation branch (`self.pk is None or self._state.adding`), alongside the existing
  `_validate_switch_type_port_profile()` call.

A missing range is still *not* an error, per decision 5 — the pre-flight only checks the
ranges that exist.

This departure needs a note added to ADR 0016 recording why its stated reasoning didn't
survive contact with the admin's save ordering.

## Admin

- **`NetworkSwitchAddForm`**, mirroring `NetworkDeviceAddForm` (`admin.py:325`): an
  `address_materialization` `ChoiceField`, `required=False`, `initial=SwitchAddressing.STATIC`,
  assigned to `self.instance` in `_post_clean()` **before** `super()._post_clean()`, which is
  what calls `full_clean()`. Use `self.cleaned_data.get(...) or SwitchAddressing.STATIC` —
  `required=False` means a blank submission cleans to `""` rather than being absent, so a
  bare `.get()` default doesn't cover it.
- **`NetworkSwitchAdmin.get_form()`** returns that form only when `obj is None`; the change
  form omits the field entirely rather than showing one that does nothing.
- **`NetworkSwitchAddressInline.has_add_permission()` must return `False` when `obj is None`.**
  This is the second thing ADR 0016 doesn't address. The inline (`admin.py:143`) currently
  allows adds, unlike `NetworkDevicePortInline` (`:550`), and Django saves the parent
  (`save_model()` → materialization) before the inline formsets (`save_related()`). An
  operator creating a switch and typing an address inline on the same page would get both
  rows for the same VLAN — an `IntegrityError` on `unique_switch_vlan_address`, a 500 rather
  than a form error. Materialization cannot avoid this by inspection, because those rows do
  not exist yet when it runs.

  Blocking adds on the Add page makes it unreachable, and matches how devices already behave.
  `MANUAL` then means "create the switch, then add its addresses on the change page" — a
  two-step. The change page keeps full add / edit / delete, so nothing becomes impossible.

  Note that `UnsavedParentInlineSuggestionTests.test_switch_address_suggested_for_inline_on_unsaved_new_switch`
  (`tests.py:487`) exercises the formset directly rather than through the admin, so it does
  not break — but its docstring's claim about "one admin Add page" becomes untrue for
  switches and should be corrected.

## Coverage

ADR 0016 names five cases; the departures above add three more.

From the ADR:

- The default path materializes one address per rack range, with correct `base + slot` values.
- `MANUAL` materializes none.
- An unracked switch materializes none under either choice.
- A rack with no ranges produces a switch with no addresses **and no error**.
- A collision rolls back the switch and every address created before it — assert both that
  `NetworkSwitch.objects.count()` is unchanged and that no orphan `NetworkSwitchAddress` rows
  survive.

Added here:

- **An admin POST to `/admin/inventory/networkswitch/add/` with a colliding address renders a
  form error, not a 500** — the switch-side twin of
  `test_admin_add_post_address_collision_renders_form_error_not_500`, and the whole
  justification for the pre-flight.
- **`address_materialization` rejects an out-of-domain value** with `ValidationError`, and
  `NetworkSwitch.objects.create(address_materialization=SwitchAddressing.MANUAL)` works —
  i.e. the property is a `property`, not a class attribute.
- **Addresses are materialized in `vlan__vlan_id` order** — create a rack whose ranges' VLAN
  ids sort differently from their pks or names, and assert the resulting order.

## Consequences accepted, not solved

Recorded in ADR 0016 and not addressed by this plan:

- A switch gets an address on **every** VLAN its rack has a range for, needed or not. The
  alternative is per-switch VLAN selection at creation, which reintroduces the hand-entry
  the ADR removes.
- A racked switch **cannot be marked DHCP-managed** — `NetworkSwitchAddress` has no `is_dhcp`
  field, so "takes its management address from DHCP" is representable only as the absence of
  rows. Pre-existing, but this ADR makes that absence meaningful for the first time.
- The cross-table switch/device address race (#5) is untouched. No DB constraint spans
  `NetworkSwitchAddress` and `NetworkDevicePort`, so concurrent allocations can still both
  validate and collide. Exercised more often, not worsened in kind.
