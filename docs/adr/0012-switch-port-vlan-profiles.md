# Switch Port VLAN Profiles: a live-referenced exception to ADR 0010's seed-once rule

`NetworkSwitchTypePort`/`NetworkSwitchPort` used to carry their own `port_mode`/`native_vlan`/`allowed_vlans`. DESIGN.md's "Switch Configuration" section identified the resulting problem: many ports share one general purpose ("Dante Primary", "Audio Trunk") but differ only in number and description, so that VLAN config was retyped on every port of every profile, and there was no way to redefine what "Audio Trunk" means without editing each port by hand. `SwitchPortVlanProfile` is the fix — a reusable, named bundle of `port_mode`/`native_vlan`/`all_vlans_allowed`/`allowed_vlans` that a type port or instance port points at.

**Live reference, not seed-once.** Every other field ADR 0010 introduced (`port_type`, a device port's `description`/`vlan`, a type's declared `port_count`) is materialized *once*, at creation, and never re-synced — the whole point being that "this profile" always means one fixed, frozen layout. A `SwitchPortVlanProfile` reference works the opposite way on purpose: `NetworkSwitchTypePort.profile`/`NetworkSwitchPort.profile` store the profile's id, not a copy of its `port_mode`/`native_vlan`/`allowed_vlans`, so every read goes through the live row. Editing a profile's allowed VLANs reaches every port using it immediately, including ports on switches that already exist. This is a deliberate, narrow departure from ADR 0010: the entire reason a profile is named and reusable is to redefine it fleet-wide in one place, which a seed-once copy would defeat.

**What locks, and when.** `port_mode`/`native_vlan` lock once any real `NetworkSwitchPort` references the profile — not merely a `NetworkSwitchTypePort`, since a profile still being wired into type definitions has no real port depending on its exact VLAN yet (mirrors ADR 0010's "locks once it has any instance", just one level further out). `allowed_vlans`/`all_vlans_allowed` stay editable even once in use: adding a tagged VLAN to an already-deployed trunk is the profile's whole reason to exist. `name` is never locked (cosmetic). The system default profile (`is_system=True`, see below) locks all three scalars — including `all_vlans_allowed` — permanently, since it's the documented fallback every unselected type port lands on; `is_system` itself is immutable after creation, enforced the same way every other locked field in this module is, so it can't be flipped off to unlock or delete the row.

**Four enforcement paths for three `allowed_vlans` invariants, not one `clean()`.** The invariants — the native VLAN must not also appear in `allowed_vlans`; no allowed VLANs while `all_vlans_allowed` is set; no allowed VLANs in Access mode — can't live in `SwitchPortVlanProfile.clean()`: a new profile has no pk yet, so its M2M manager can't be queried, and for an edited profile `ModelForm.save_m2m()` runs *after* `save()`, so `clean()` would only ever see the previous links. Each path validates the state it can actually see: the admin form's `clean()` (the submitted complete state, and the only path that can produce a field-level form error); an `m2m_changed` receiver on `allowed_vlans` (`.add()`/`.set()` write the through table directly and never call the profile's own `save()`); `SwitchPortVlanProfileAllowedVlan`'s own `clean()`/`save()` (direct through-row creation, which fires neither the form nor `m2m_changed`); and the profile's own `save()`, re-checked against *already-persisted* links whenever a scalar changes (catches, e.g., flipping `all_vlans_allowed` to `True` while links already exist — none of the other three paths see that case). The `m2m_changed` receiver is the one signal in this module, which otherwise avoids them entirely — it is the only hook Django offers for `.add()`/`.set()`/`.clear()`.

The receiver locks the profile row and then **re-reads that row's scalars from the database** rather than validating the caller's in-memory `instance`. Taking a lock and then trusting a cached object is lock-shaped, not lock-safe: the caller's copy can predate a concurrent, already-committed change to `native_vlan`/`port_mode`/`all_vlans_allowed`, so the lock would serialize the critical section while the check still read stale values — exactly the race the lock exists to close. (Known remaining gap, accepted for now: `SwitchPortVlanProfileAllowedVlan._validate_against_profile` still reads its cached related profile without a lock, and `_in_use()` is a non-locking snapshot read.)

**Row locking follows the profile's actual usage, not just its own edits.** Beyond editing the profile itself, three other operations change whether it's "in use": creating a real `NetworkSwitchPort` (including materialization), changing a port's `profile` from one to another, and deleting a port. Each locks the affected profile row(s) (`_lock_profile_rows`, `SELECT ... FOR UPDATE`) before checking state, the same pattern `_lock_type_rows` established for Type Profiles — otherwise a concurrent native-VLAN edit and a concurrent port materialization could each observe a stale "not locked yet" state and both proceed. `NetworkSwitchPort.save()` is the single enforcement point for this (materialization goes through it too), rather than duplicating the guard in `_materialize_ports()`.

**Swapping a port's profile is blocked once a device is connected**, per DESIGN.md: `NetworkSwitchPort.profile` cannot change while `NetworkDevicePort.switch_port` points at it — disconnect, swap, reconnect. `InlineModelAdmin.get_readonly_fields()` can't express this (it receives the parent switch, not each port, and its result applies to the whole formset), so `NetworkSwitchPortForm` disables the field per row in `__init__` instead; the model-level guard in `NetworkSwitchPort.save()`/`clean()` still stands for direct ORM/API writes. The connect/disconnect side of this (`NetworkDevicePort.switch_port`) locks the same `NetworkSwitchPort` row before checking, closing the symmetric race.

**VLAN 1 is a real, system-seeded VLAN with no subnet.** DESIGN.md's default profile specifies "Native VLAN: 1", and rather than inventing a subnet for a VLAN nobody asked to track, `VLAN.subnet` becomes optional (`blank=True`). A subnet-less VLAN is **L2-only**: it can be a profile's native or allowed VLAN, or a device type port's VLAN (DHCP only), but `default_gateway`/`dhcp_range_start`/`dhcp_range_end` must be blank (backed by a DB `CheckConstraint`, `vlan_subnetless_has_no_addressing`) and it can never have a `RackVlanRange`, a static `NetworkSwitchAddress`, or a static `NetworkDevicePort` address — those are model-validation guarantees only (no DB constraint can span tables), with the same `QuerySet.update()`/`bulk_create()` bypass limitation this module already documents elsewhere. The seeded VLAN is named "Default VLAN" (`vlan_id=1`); the seeded profile is named "Default", `is_system=True`, `all_vlans_allowed=True`, `port_mode=Trunk` — exactly DESIGN.md's "Switch Port Profile VLAN Selection" fallback. `NetworkSwitchTypePort.profile`/`NetworkSwitchPort.profile` default to it via a callable (`default_switch_port_vlan_profile()`) that resolves the row *at call time*, never a pk cached at import time.

**Migration is destructive, same posture as ADR 0010's own.** This project's local databases are rebuilt, not migrated over — there is no attempt to translate existing `port_mode`/`native_vlan`/`allowed_vlans` into generated profiles; every type port/port is pointed at the seeded Default instead. If real data ever exists before this runs, a staged backfill must be written first. The seed step fails loudly (`RuntimeError`) if a pre-existing row conflicts with the documented seed state, rather than silently adopting it as "the" Default; its reverse is a documented no-op, since there is no way at reversal time to tell a row the migration created from one it merely found. A `seed_defaults` management command (parallel to `sync_roles`) re-seeds both rows if they're ever removed outside a migration — e.g. by `manage.py flush`, which a migration has no way to repair after the fact.

**Both seeds identify the system profile by `is_system=True`, never by `name`.** `name` is deliberately editable even on the system row (it's a cosmetic label), so it is not a stable identity. Keying the seed on the name would mean a single supported rename caused the next `seed_defaults` run — which `docker/entrypoint.sh` performs on *every* container start — to create a **second** `is_system=True` row, after which `default_switch_port_vlan_profile()` raises `MultipleObjectsReturned` on every switch-port creation, with neither row deletable through the app to recover. If no system row exists but the default name is already taken by an ordinary profile, both seeds fail with an actionable error rather than an opaque `IntegrityError` on the unique `name`.

**Known gap, same root cause as ADR 0010's:** `SwitchPortVlanProfile.allowed_vlans` isn't a field `_check_locked_fields_unchanged` can check (M2M managers don't go through `Model.save()` at all). Its own locking/validation lives in the `m2m_changed` receiver and the through model's `save()`/`clean()` instead; a raw `bulk_create()` against `SwitchPortVlanProfileAllowedVlan` still bypasses both and is unsupported, consistent with the `QuerySet.update()`/`bulk_create()` gap this module already carries for locked fields generally.
