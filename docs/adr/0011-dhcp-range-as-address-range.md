# DHCP range is a manual start/end address range, not a CIDR block

`VLAN.dhcp_range` was originally a single CIDR field (e.g. `10.200.0.0/24`), suggested on creation as the bottom `/24` of the subnet — see [ADR 0002](./0002-network-sizing-dhcp-convention.md). That representation forces every DHCP range to a power-of-two, octet-aligned block, which does not match how DHCP pools are actually configured on real equipment: an operator needs to hand a DHCP server an arbitrary start/end pair (e.g. `10.200.0.10`–`10.200.0.200`), not a subnet-shaped block. The CIDR-based field was unusable for that case, so it is replaced with `dhcp_range_start`/`dhcp_range_end`, a pair of plain IPv4 addresses (`GenericIPAddressField`, the same type `default_gateway` already uses) representing an inclusive range. This supersedes the DHCP-range-suggestion half of ADR 0002 — the `/21`-default / bottom-`/24` *network sizing* convention in ADR 0002 is unchanged, only its "suggest the bottom `/24` as the DHCP range, snapped to octet boundaries" guidance is superseded, since there is no longer any suggestion at all (see below).

The two fields are optional but paired: both must be set or both left blank (enforced by a DB `CheckConstraint`, `vlan_dhcp_range_start_end_together`, mirroring the same all-or-none pattern already used for `NetworkSwitch.rack`/`rack_slot`). When both are set, `VLAN.clean()` enforces: `dhcp_range_start` strictly less than `dhcp_range_end` (a single-address range is rejected — a DHCP pool needs at least two addresses to be useful); both addresses fully within the VLAN's subnet; the range must not contain the subnet's network address (not a valid host address) or its broadcast address; and, when a default gateway is set, the range must not contain it either. On an edit to the VLAN's subnet or DHCP range, the same re-validation that already ran for `RackVlanRange` blocks and existing static addresses (see `VLAN.clean()`) now also checks the DHCP range against them — an edited range can just as easily swallow an already-assigned static address as an edited subnet can exclude one. Symmetrically, `_address_containment_error` (the shared containment check behind `NetworkSwitchAddress`/`NetworkDevicePort` creation) now also rejects a *new* static address that falls inside the VLAN's DHCP range, so the exclusion is enforced at the point an address is assigned, not only rediscovered later on a VLAN edit.

Because start/end has no natural CIDR-vs-CIDR overlap check, a small helper (`dhcp_range_overlaps_cidr`) does interval-overlap between an address range and a CIDR block; it replaces the old `ranges_overlap` CIDR-vs-CIDR check everywhere `dhcp_range` used to be compared against a `RackVlanRange.address_range` block (both in `RackVlanRange.clean()`'s next-free-block suggestion, and in its own overlap validation).

Auto-suggestion is dropped entirely, not replaced with an equivalent start/end algorithm — the old suggestion's whole rationale was snapping to a `/24` boundary, and no replacement convention was wanted. `dhcp_range_start`/`dhcp_range_end` are always manual entry, same as before but without the "suggest once on create" step; a VLAN can still have no DHCP range at all.
