# Port profiles: types are purpose profiles, materialized once, locked after creation

> **Partially superseded by [ADR 0012](./0012-switch-port-vlan-profiles.md).** Everything below about type immutability, materialization, and locked fields still holds. What doesn't: `NetworkSwitchTypePort`/`NetworkSwitchPort` no longer carry their own `port_mode`/`native_vlan`/`allowed_vlans` — both now point at a `SwitchPortVlanProfile` instead, referenced *live* rather than materialized once. The "Known gap" note below about `NetworkSwitchTypePort.allowed_vlans` no longer applies to that field, which no longer exists; the equivalent gap now lives on `SwitchPortVlanProfile.allowed_vlans` — see ADR 0012.

A Network Switch/Device Type is a *purpose profile* built on a hardware model, not the bare hardware model itself — the same physical switch or device commonly needs several different profiles, because what each port is *used for* varies even though the hardware doesn't (e.g. a Cisco SG350-10MP wired for a drive rack vs. the identical switch wired for an amp rack; a Martin Audio IK-42 with a Dante card vs. without one). A Type is therefore identified by `(manufacturer, model, name)`, where `name` is a required, non-blank profile label — this keeps the type selector unambiguous for an audience that may not have deep VLAN/subnetting knowledge. Each profile owns a list of `NetworkSwitchTypePort`/`NetworkDeviceTypePort` template rows describing each port's physical type and VLAN purpose.

When a switch or device is first created, its type's port templates are copied exactly once into real `NetworkSwitchPort`/`NetworkDevicePort` rows (`_materialize_ports`, run inside the same transaction as the parent's own insert) — never re-synced afterward. Device ports materialize as DHCP-configured (`is_dhcp=True`, no address); an operator gives one a static address afterward. A profile must be complete (its port count matches its declared `port_count`, and for switches, its port numbers form a contiguous `1..N` sequence) before it can be used to create an instance.

Two things are locked to keep "this profile" meaning one fixed port layout, and to avoid silently discarding an instance's configuration:

- **A switch/device's type is immutable after creation.** Re-typing (e.g. adding a Dante card to an amp) means removing and recreating the instance, not editing the type field. The alternative — allowing the type to change and re-materializing ports — would silently discard DHCP state, switch-port overrides, and connections every time.
- **A profile's identity (`manufacturer`/`model`/`name`), type ports, and its declared `port_count` all lock once the profile has any instance.** Changing a profile's port layout — or silently renaming it out from under instances that already reference it — after it's in use would leave existing instances holding a stale copy with no way to reconcile; create a new named profile instead.

On the instance ports themselves: a switch port's `switch`, `port_number`, physical `port_type`, and `source_type_port` (provenance) are locked — they identify which physical port this row *is* — but its VLAN purpose (native/allowed VLANs, mode, description) stays editable per switch. A device port's `device`, `port_number`, `ordinal`, `description` (purpose), `vlan`, `port_type`, and `source_type_port` are all locked; only `is_dhcp`/`address`/the connected switch port are editable. Locking ownership (`switch`/`device`) and `port_number`/`ordinal` alongside the hardware/purpose facts closes a gap where a plain `save()` could otherwise move a materialized port to a different switch/device or renumber/reorder it, corrupting the seed-once copy of the profile it came from (PR #17 review). A device port's default gateway is never stored — it's a read-only property derived live from its VLAN, so it can't go stale if the VLAN's gateway is edited later.

These guards are enforced inside `save()` itself, not only `clean()` — Django does not call `clean()`/`full_clean()` from `save()`, so a plain `instance.save()` would otherwise bypass them. `QuerySet.update()` and `bulk_create()` still bypass `save()` entirely and are unsupported for these locked fields. A type-port's own `save()` **and `delete()`** (and a bulk `QuerySet.delete()` on its manager) also reject reassigning or removing a row out from under a profile that's already locked — checked against the row's *persisted* parent, not just its in-memory one, on both paths, so reassigning a locked type-port to a different, unlocked profile in memory can't bypass the check by immediately calling `delete()` instead of `save()`. Everywhere a profile's lock state is checked, the type row is locked (`SELECT ... FOR UPDATE`, inside `transaction.atomic()`) first, so a concurrent instance-materialization and a concurrent profile edit can't each observe a stale "not locked yet" state and both proceed.

A switch/device's `save()` decides whether to materialize by checking `self.pk is None or self._state.adding` — not either alone. `_state.adding` alone is wrong when a pk is pre-assigned (fixtures, scripted inserts) before the row actually exists; `pk is None` alone is wrong after `instance.delete()` (which Django resets to `None` but never flips `_state.adding` back to `True`), which would otherwise let a re-`save()` of the same in-memory instance silently insert a switch/device with zero materialized ports. A Device Type Port's auto-assigned `ordinal` is likewise finalized inside `save()`'s lock, not trusted from whatever `clean()` computed beforehand — admin formsets run every row's `clean()` before any row is saved, so two new ports added to one profile in the same submission would otherwise both compute the same "next" ordinal and collide.

Because a few of the above are only checked at `save()`/`delete()` time — not `clean()` — Django admin's normal "invalid form, show the error" flow doesn't apply to them (that flow only catches `clean()`-raised errors). `AuditedModelAdminMixin.changeform_view` catches a `ValidationError`/`IntegrityError` raised this way and redirects back with a message instead of surfacing an unhandled 500.

**Known gap (documented, not closed):** a locked `NetworkSwitchTypePort`'s `allowed_vlans` can still be changed via `.add()`/`.remove()`/`.set()`/`.clear()` on the M2M manager — those write the `NetworkSwitchTypePortAllowedVlan` through table directly and never call `NetworkSwitchTypePort.save()` or its lock check, for the same reason `QuerySet.update()`/`bulk_create()` bypass locked-field enforcement above. Unsupported for now; see the "Known gap" note on `_check_locked_fields_unchanged` in `inventory/models.py`.

`allowed_vlans` (on both the type-port template and the instance port) uses an explicit through model with a `PROTECT` foreign key to VLAN, rather than a plain `ManyToManyField`'s auto-generated join table — a VLAN referenced only through an auto-generated M2M table can't be protected from removal at all (ADR 0007), since Django's deletion collector doesn't traverse plain M2M relations. The explicit through model closes that gap for both single-object and bulk/queryset deletion.

**Known deferred limitation:** a device port is always single-VLAN/single-address. Hardware where two physical jacks are bridged into one logical interface sharing one IP (e.g. Shure ULXD4Q/D "Switched" mode) can be tracked as two ordinary ports here, but the system won't stop them from being given two different addresses, which wouldn't reflect the real, single-IP hardware. Modeling this correctly would need a logical-interface concept distinct from the physical port/jack — deferred to a later phase.

**Migration workflow: local databases are rebuilt, not migrated over.** This phase's migration adds `NetworkDevicePort` constraints (`unique(device, description)`, `unique(device, ordinal)` with `ordinal` defaulted to `0`, a non-blank `description` check) and narrows `port_type` from free text to a fixed `choices` enum with no data-mapping step. Neither is written to tolerate arbitrary pre-existing rows — a device with more than one existing port, a blank description, or an out-of-domain `port_type` value will fail to migrate or (for `port_type`, since Django `choices` aren't DB-enforced) migrate into a permanently-locked invalid value. This is deliberate, not an oversight: no production data exists yet, so the migration is only ever run against a freshly rebuilt local database. If that stops being true, a staged backfill migration must be written before applying this migration to a database with real rows.
