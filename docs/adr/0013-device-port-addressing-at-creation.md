# Device port addressing at creation: static by default, revising ADR 0010

Creating a device in a rack always materialized its ports as DHCP (`is_dhcp=True`, `address=None`) — a deliberate ADR 0010 decision. In practice, racked devices are statically addressed, so every device creation was followed by hand-editing each port. This closes #24: device creation now offers a DHCP-or-static choice, **defaulting to static**, computed in the usual rack-range-base + rack-slot style `suggest_slot_address()` already uses everywhere else.

**The choice is transient, never stored.** No migration, no new column. `NetworkDevice.port_addressing` is a writable `@property` over a private `_port_addressing` class-level default (`PortAddressing.STATIC`) — not a plain class attribute. Django's `Model.__init__` only accepts an unknown keyword when the name is a field or a `property` (`opts._property_names`), so a property is what makes `NetworkDevice.objects.create(..., port_addressing=PortAddressing.DHCP)` work at all; a plain class attribute would raise `TypeError` from that call. The setter rejects anything outside `PortAddressing.values`, raising `ValidationError` rather than silently falling through to DHCP — a non-property attribute would have let an invalid value through unchecked. The materialized `NetworkDevicePort` rows are the only record of what was chosen; a stored field would go stale the moment an operator flips one port to DHCP by hand, so there is deliberately nothing to keep in sync.

**Default is static everywhere** — the admin add form and programmatic `NetworkDevice.objects.create()` alike. "Default static" is a domain rule, not a UI quirk that only the admin knows about.

## The constraint that shapes the design

`suggest_slot_address()` (`inventory/suggestions.py`) yields exactly **one** address per `(rack slot, VLAN)`: the rack's assigned range base for that VLAN, plus the slot number. A rack slot holds one piece of equipment (enforced per-table in the DB, and across switches/devices by a `full_clean()`-time cross-table guard), so that address is unambiguous — *as long as each of a device's ports is on a different VLAN*. Every device shape in DESIGN.md's "Concrete Device Examples" satisfies that except **Switched Mode** (Shure ULXD4Q/D, and the generic 2-port case), where both jacks sit on Dante Primary.

The root cause is that an address is modeled as a property of the *port* rather than of the *(device, VLAN)* pair — which is also exactly what ADR 0010 already deferred under "bridged multi-port logical interfaces." Fixing that properly (a logical-interface concept distinct from the physical port/jack) is a much larger change, filed separately as #27. Switched Mode is rare in practice here (dual-port Dante devices normally run in Redundant mode, one VLAN per port, which addresses fine), so **static materialization refuses those devices with a clear error naming both ports** rather than inventing a second address the hardware doesn't have. DHCP remains available for them — explicitly, or by leaving the device unracked.

## Decisions

1. **Choice is transient, not stored** (see above).
2. **Default is static everywhere** (see above).
3. **Unracked devices always materialize DHCP**, whatever the choice says. The spare pool is DHCP by definition (CONTEXT.md); `NetworkDevicePort.clean()` already rejects static addresses on unracked devices, so this is enforced twice over — once by `_materializes_static()` never returning true for an unracked device, and once by the port's own `clean()` if that were ever bypassed.
4. **A port on an L2-only VLAN always materializes DHCP, even under a static choice, and this is not a failure.** A subnet-less VLAN (ADR 0012) can never carry a static address, so DHCP is that port's only legal state — refusing the whole device here would make static addressing unusable for any type with an L2-only port (e.g. a device type port that only carries Shure control traffic on the system Default VLAN).
5. **Otherwise, static materialization fails the entire device creation — never a half-configured device** — when a port that *could* be addressed can't be: duplicate VLAN across ports (Switched Mode's shape), no usable `RackVlanRange` for a port's VLAN on this rack, or a collision with an existing address. "Collision" means everything `_validate_static_address()` can see; the cross-table switch/device race (#5) is a pre-existing, documented gap that this work neither closes nor worsens in kind — it's simply exercised more often now that static materialization runs by default.

## Implementation

`NetworkDevice._check_static_materialization_possible()` is a pure pre-flight over the device type's ports, needing no device pk — it runs from both `NetworkDevice.clean()` (so the admin renders a normal form error) and the top of `_materialize_ports()` (since `save()`/`objects.create()` never call `clean()`; skipping the direct-ORM path would otherwise let a duplicate-VLAN device fail with a generic address-uniqueness error deep inside the second port's `full_clean()`, instead of the deliberate, two-port-naming error this ADR promises). It skips L2-only-VLAN ports entirely (decision 4), groups the rest by VLAN to catch duplicates (decision 5), and calls the same `_suggest_rack_slot_address()` / `_validate_static_address()` helpers `NetworkDevicePort.clean()` already uses, so there is exactly one place that decides whether a rack-slot address is usable.

`_materialize_ports()` builds each static-eligible `NetworkDevicePort` unsaved (`is_dhcp=False, address=None`) and calls `port.full_clean()` before `save()` — reusing `NetworkDevicePort.clean()`'s existing blank-address-fill-and-validate logic rather than duplicating allocation arithmetic. This works because `address` is `null=True, blank=True` at the field level, so `clean_fields()` passes on the blank value, `clean()` fills it from `_suggest_rack_slot_address()` and validates it, and only then does `validate_constraints()` evaluate `device_port_dhcp_xor_static_address`. An L2-only port, or any port under an explicit DHCP choice, keeps today's `NetworkDevicePort.objects.create(is_dhcp=True, ...)` path unchanged. Everything runs inside the existing `transaction.atomic()` in `NetworkDevice.save()`, so any failure rolls back the device and every port materialized before it — no half-configured device is ever left behind.

The admin's `NetworkDeviceAddForm` carries `port_addressing` as a non-model `ChoiceField` (`initial=STATIC`), used only for the add view (`NetworkDeviceAdmin.get_form()` swaps it in when `obj is None`) — the choice has no effect after creation, so the change form doesn't show a field that would do nothing. `_post_clean()` sets `self.instance.port_addressing` from `cleaned_data` before calling `super()._post_clean()` (which is what runs `instance.full_clean()`); it reads via `cleaned_data.get(..., PortAddressing.STATIC)` rather than indexing directly, since the `ChoiceField`'s own validation already rejects an out-of-domain submission before `cleaned_data` is populated, leaving the key absent rather than raising here.

## Known gap, unchanged

The `unique_device_port_vlan_address_value` DB constraint is the in-table backstop against a collision this ADR's pre-flight missed. The cross-table switch/device race (#5) — no DB constraint spans both tables, so a concurrent switch-address and device-port-address allocation on the same VLAN can still both pass validation and collide — is untouched by this work. Static materialization now runs by default instead of opt-in, so this gap is exercised more often, but the gap itself is pre-existing and out of scope here.

## Follow-up

Addressing modeled per `(device, VLAN)` instead of per port — the actual fix for Switched Mode — is filed as #27 and parked in `ROADMAP.md`'s "Later" section.
